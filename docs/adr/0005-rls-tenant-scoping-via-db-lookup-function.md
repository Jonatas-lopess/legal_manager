# RLS resolves tenant_id via a DB-lookup function, not a session variable

PLANNING.md originally described RLS policies filtering on `current_setting('app.tenant_id')`, which requires a backend to `SET LOCAL` that variable per request. This architecture has no such backend — the client talks directly to PostgREST (§4) — so that mechanism cannot work as written. Considered a Supabase custom-JWT-claim (Auth Hook embeds `tenant_id` into the token) as the alternative. Decided instead on a `SECURITY DEFINER` SQL helper function that looks up `tenant_id` from `public.users` by `auth.uid()`, with RLS policies comparing `tenant_id = current_tenant_id()`. No Auth Hook configuration needed, and it can't go stale the way a cached JWT claim could if a user's tenant ever changed before token refresh. Every RLS policy across every tenant-scoped table depends on this function's contract, so changing the mechanism later means rewriting every policy, not just a config flag.
