# Personal ABAC permissions replace the fixed role enum (design-only)

PLANNING.md §5/§8 left "papéis customizáveis por tenant" as an undecided post-MVP hook, warning only that the permission layer shouldn't get hardcoded to the 3 MVP roles (`admin`/`advogado`/`secretario`) to the point of blocking that extension. This ADR resolves the design (not the implementation — no code changes yet) after grilling three shapes: per-tenant override flags on the 3 fixed roles, fully custom named roles per tenant (`roles`/`role_permissions` tables), and direct per-user attribute-based grants. Decided on the third: a `permissions` catalog of `(resource, action, scope)` tuples plus a `user_permissions` join granting them directly to individual users — no `roles` or `role_permissions` table, no role name, anywhere. `users.role`/`userRoleEnum` is retired in this design entirely, replaced by a single `tenants.administrator_id` (exactly one admin per tenant, unconditional bypass of every permission check) plus per-user grants for everyone else. This also reframes the previously-flagged gap of "no way to provision a second admin" as intentional — one FK column structurally allows exactly one admin — rather than an oversight.

`scope` is `own` or `tenant`, set independently per `(resource, action)` pair rather than fixed per resource (e.g. a user can hold `matters:read:tenant` plus `matters:update:own` at once). Ownership is anchored solely on `matters.responsible_id`; child resources like `payments` have no ownership column of their own and resolve `own` by joining up to their parent matter's `responsible_id`. The catalog stays deliberately minimal — only resources with real gating need today get rows: `matters`, `payments`, `clients` (added ahead of need for LGPD art. 5º II sensitive data eventually linked to a client), `users` (invite/management), and `reports`. `matter_catalog_items`, `deadlines`, and `tags`/`matter_tags` stay fully open to any tenant member, matching today's behavior — same "don't wall off what nobody asked for" reasoning as ADR-0001, which this ADR extends rather than reverses: the invite-time starter bundle (below) seeds the `tenant`-scope default for `matters`, preserving ADR-0001's no-isolation default until an admin narrows it per user.

Enforcement is primarily RLS, via a `current_user_can(resource, action, scope)` `SECURITY DEFINER` helper mirroring ADR-0005's `current_tenant_id()` pattern — the sensitive-data stakes named in PLANNING.md §8 (LGPD/sigilo profissional) justify the same defense-in-depth already given to tenant isolation, not a weaker app-only guarantee. An app-layer `can()` convenience stays for early, friendly error messages, but RLS is the actual backstop. On invite, a new user is seeded with a one-time, code-defined starter bundle of `user_permissions` rows (mirroring today's default `advogado` access) — copied once, no live link to anything nameable as a "role." The tenant's own `administrator_id` grants/revokes individual rows afterward, self-serve, the same way they already manage invites.

Out of scope here: migrating the 5 existing inline role checks (`payments.service.ts`, `reports.service.ts` ×3, the invite Edge Function's admin gate) and dropping `userRoleEnum` from `packages/db`. Written up when this is actually pulled into a sprint, not now.
