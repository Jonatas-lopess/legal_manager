## Comments

- 2026-09-11: Implemented. `ClientsTable.tsx` relayout: header title/search/status-filter/"Novo cliente" merged into one flex row (`justify-between`, title left, controls right); table now wrapped in the `Card`/`CardContent` pattern (`MatterDetailView.tsx`'s convention) instead of a bare `rounded-xl border` div; columns reordered/collapsed to Nome / Razão social | CPF/CNPJ | Telefone | E-mail | Status (pill) | Ações, with header labels kept as normal-case text (`uppercase` Tailwind class doing the visual transform, not literal caps strings) per this app's pill/header convention; loading state now renders 5 skeleton `<tr>`s (`Skeleton` from `components/ui/skeleton.tsx`) inside the real `<table>` (kept the header visible during load) instead of a bare "Carregando..." string; empty state is a centered message + "Novo cliente" CTA inside a full-width table cell instead of a bare "Nenhum cliente encontrado." line.
- **Archived/`deletedAt` vs. `status` judgment call**: the ticket's "archived (soft-deleted, `deletedAt` set) rows render visually muted... still in the filtered list when `status=inativo` is selected" can't be literally true against real data — `clients.repository.ts`'s `listClients()` unconditionally does `.is("deleted_at", null)`, so `deletedAt` is always `null` on every row `ClientsTable` ever receives (confirmed again by the passing `clients.service.test.ts` "soft-delete hides from the default list" case, unchanged by this ticket). Read this as the ticket text loosely conflating "archived" with the real, reachable `status: "inativo"` signal. Implemented: mute a row when `client.status === "inativo"` **or** `client.deletedAt !== null` — the second check is a currently-inert no-op (defensive/future-proofing only) given the hard repository filter, kept so the code still matches the ticket's literal wording without any extra risk. Flagging in case this reading is wrong, but not blocking on it per the task brief.
- **"Arquivar" relabel**: renamed the row action from "Excluir" to an icon-only button with `aria-label="Arquivar {name}"` (still calling the same `softDeleteClient`, no behavior change) to match the wireframe's "archive" framing rather than "delete". Also updated the `window.confirm` copy's leading verb from "Excluir" to "Arquivar" for consistency with the new label — the rest of that copy ("mantido para fins de auditoria") was already archival-flavored and needed no change.
- **`lucide-react` introduction**: first real usage of the already-installed-but-unused `lucide-react` (^1.34.0) dependency — `Pencil`/`Archive` icons for the AÇÕES column, rendered via icon-only `Button size="icon" variant="ghost"` with a descriptive `aria-label` each (no visible text label, per the frame's icon-based actions column). No new icon library introduced.
- **`ClientDialog.tsx` field order + Status field removal**: reordered to nome, cpf, cnpj, rg, data de nascimento, telefone, e-mail, endereço, estado civil, profissão, parte contrária, procuração, observações — exactly the ticket's list. That list (and the identical list in `spec.md`'s original text brief, which this ticket's own frame is said to match "almost exactly") has no `status` field at all, so I removed the `<select>` for `status` from the form entirely rather than just moving it — status is no longer editable from the create/edit dialog, matching what's actually drawn. This is safe: `react-hook-form`'s `defaultValues` still seed `status` (`client?.status ?? "ativo"`) into the form's internal value object even with no registered input for it, so the submitted payload still carries the correct value on every save — `"ativo"` on create, the client's current (possibly `"inativo"`) status preserved unchanged on edit. No zod-`.partial()`-default-resurrection bug involved (that bug — noted in `packages/schema/src/index.ts`'s comment near `updateMatterInputSchema`, and flagged there as also latent on `clients` — only fires when a key is *omitted* from the input object entirely; here the key is always present, just not user-editable). Flagging this call explicitly since it's a real behavior change (one less thing editable via the dialog), not asked for in so many words — but it's what "field order matches exactly" against a `status`-free list implies, and it's consistent with status now being archive-controlled from the list's Ações column instead.
