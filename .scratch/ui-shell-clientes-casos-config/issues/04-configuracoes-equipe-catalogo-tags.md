## Comments

- 2026-09-11: Implemented. `/settings` registered in `App.tsx`'s `ProtectedApp` switch, new `apps/web/src/components/SettingsPage.tsx` (title + tab strip + one card, matching AppShell's own top-level-component precedent — not placed inside any one module since it aggregates three of them). - **Guardrail placement (the trap section's main ask) — both enforced server-side in `supabase/functions/tenants/service.ts`'s new `removeMember`, with light UI-disable on top of the already-known-static case:**
  - **Self-removal**: server-rejects (400, "Você não pode remover a si mesmo.") *and* UI-disables "Excluir" on the caller's own row (`MembersTable.tsx`'s `isSelf`). Server is authoritative; the UI disable is pure affordance (matches the ticket's "disable where statically known" note) — a user with a stale member list can't bypass it since the server check runs regardless.
  - **Last admin**: server-rejects (400, "Não é possível remover o último administrador do escritório.") in `removeMember`, plus a UI disable (`isLastAdmin`) computed from the same member list's admin count. Wrote this up in detail because it's non-obvious: given the admin-only gate (caller must be an admin of the same tenant), whenever a target is a tenant's *sole* admin, the caller is necessarily that same admin — there is no code path where a *different* person triggers the last-admin guard against someone else, since a second admin existing would mean the target isn't the sole admin. So the last-admin guard is, today, only ever reachable through a sole admin removing themselves — a strict subset of the self-removal scenario. To keep both guardrails independently meaningful (and independently testable, see below) rather than one silently dead-coding the other, `removeMember` checks **last-admin first, self-removal second**: a sole admin removing themselves gets the more specific "you're the last admin" message, while an admin removing themselves *when other admins exist* still gets blocked by the (broader, unconditional) self-removal check with its own message. `MembersTable.tsx`'s `isLastAdmin` UI check is consequently equivalent to `isSelf` in every reachable case today, but kept as its own explicit condition (not merged into `isSelf`) so a future role-change/demotion feature that could break this equivalence doesn't silently lose UI coverage.
  - Both guardrails also get a tenant-isolation check for free: `removeMember` looks up the target directly against Postgres (RLS doesn't apply to the Edge Function's `service_role`-adjacent direct-`pg` path) and 404s if the target isn't in the caller's own tenant, mirroring `fetchCallerMembership`'s existing bypass-RLS reasoning. Not explicitly asked for in the checklist, but spec.md's Testing Decisions explicitly calls the new function "tenant-scoped," so this is covered and tested.

- **Edge Function routing**: extended `supabase/functions/tenants/index.ts` to route by **HTTP method** (POST → `inviteUser`, unchanged; DELETE → `removeMember`, new) rather than a body discriminator field. `inviteUser`'s body (`{ email, role }`) has no discriminator today and I didn't want to change its shape just to add one; method-based routing needed only a `req.method` branch and widening the `405` guard to accept both verbs. `supabase.functions.invoke` supports `method: "DELETE"` directly (confirmed against `@supabase/functions-js`'s `FunctionInvokeOptions`), so `tenants.repository.ts`'s new `removeMember` is a one-line-different sibling of `inviteUser`.

- **Auth-vs-`users`-row delete order**: `removeMember` deletes the `public.users` row first (direct `pg` write, same reasoning as `insertTenantMember`), then calls the existing `deleteAuthUser` helper for the Supabase Auth account — the reverse of `inviteUser`'s create order (Auth user first, `users` row second). Deliberately reused `deleteAuthUser` as-is, including its `.catch(() => {})` swallow: if the Auth-account delete fails after the `users` row is already gone, the caller still sees success (the security-relevant part — tenant membership/RLS visibility — is already revoked) and the leftover Auth account is the same "orphan Auth-account-without-a-tenant-row" shape `inviteUser`'s own cleanup path already treats as acceptable, just reached from the other direction. Note the FK `users.id → auth.users.id` is `ON DELETE CASCADE` (`supabase/migrations/20260905023619_tenant-user-rls.sql`) — deleting the Auth user alone would have cascaded the `users` row for free, but writing the row-delete explicitly first (rather than relying on the cascade) keeps the same "direct Postgres write, Edge Function owns both sides" shape `inviteUser` already established, and fails loudly (no Auth account touched) if the row-delete itself fails, rather than masking a failure inside a swallowed cascade.

- **Testing**: added `removeMember` coverage to `supabase/functions/tenants/test/service.test.ts` (mirrors `inviteUser`'s existing direct-service-call pattern exactly — 7 new cases: successful removal deletes both the `users` row and the Auth user, non-admin caller rejected + nothing removed, self-removal blocked with another admin present, last-admin removal blocked, cross-tenant removal 404s, missing/invalid bearer token). Deliberately did **not** add a `removeMember` case to the frontend `apps/web/src/modules/tenants/test/tenants.service.test.ts` (the harness named in this ticket's verification section): that suite has never exercised `inviteUser` via `controller.inviteUser()` either — every existing case there tests login/session/password-reset/`listMembers` only, none of which round-trip through `supabase.functions.invoke`/the Edge Runtime. Following that established precedent (Edge Function business logic gets tested once, directly, in the Edge Function's own suite) rather than introducing a new dependency on the Edge Runtime container being reachable from the frontend suite. Widened `supabase/functions/tenants/test/harness.ts`'s `seedMember` to accept `role: "admin"` (previously `"advogado" | "secretario"` only) so the self-removal-with-another-admin-present test could seed a second admin through the existing cleanup-tracked helper instead of duplicating its internals.
  - Also found and fixed while wiring up the frontend suites in this fresh worktree: no root `.env` exists (gitignored, worktrees don't carry it) — created one from `.env.example` pointed at the already-running local `supabase start` stack so `vitest`/`vite` could resolve `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY`. Not a code change, just local environment setup; flagging in case the coordinating session's own worktree needs the same.
  - Also unwrapped the Edge Function's real JSON error body in `tenants.service.ts`'s new `removeMember` (`unwrapFunctionError`, using `FunctionsHttpError.context`) — `supabase.functions.invoke`'s rejected error otherwise always carries the generic "Edge Function returned a non-2xx status code" message, never the function's own `{ error }` body. Since the whole point of rejecting server-side "with a clear error message" (per this ticket's own text) is for the user to actually see that message, leaving it generic would have defeated it. Scoped this fix to `removeMember` only — `inviteUser` has the same latent gap but fixing it wasn't asked for here and risked colliding with unrelated behavior.
