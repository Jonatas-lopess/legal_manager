## `casos-lista` (relayout `MattersTable.tsx`, no new data logic)

- Header row: title "Casos" + search ("Buscar por número ou título...") + status filter ("Todos os status") + client filter ("Todos os clientes") + "Novo caso" button, one row above a table card (same card-wrapping change as `02`)
- Table columns: **CLIENTE** | **ITEM DE CATÁLOGO / PROCESSO** | **UF / COMARCA / MUNICÍPIO** | **STATUS** (pill) | **AÇÕES**. The second column's drawn examples ("Recurso Trabalhista - Horas Extraordinárias", "Contestação Cível - Indenização Material") read as a composed label, not a bare catalog-item name — compose it the same way this codebase's existing `matterLabel`-style helpers do (`DeadlinesTable.tsx`/`DeadlineTagPicker.tsx`: catalog item name + a short piece of `description`), don't just print `matterCatalogItemId`'s name alone.
- AÇÕES column is a bare chevron (›) — whole row is a link to `/matters/:id`, no separate edit/archive icons here (those live inside `casos-detalhe`)
- Status pill values match the enum exactly as drawn: EM ANDAMENTO, RASCUNHO, CONCLUÍDO, ARQUIVADO
- Empty/loading states, same pattern as `02`

## `casos-detalhe` (relayout `MatterDetailView.tsx`)

  2. **Prazos — NEW CARD**, not present today. Eyebrow "PRAZOS RELACIONADOS" + a `"Total: N prazos mapeados"` counter on the same header row. Deadlines scoped to this matter only (`listDeadlines({ matterId: matter.id })` — filter already exists). Grouped **vencido / hoje / próximos** — **do not call `dueDateHighlight` and stop there**: that only splits vencido/vence_em_breve/on_track, not the 3-way split this card needs. ## Comments

- 2026-09-11: Implemented. Three parts, as scoped:

  **Composed-label helper.** Neither cited precedent (`DeadlinesTable.tsx`/`DeadlineTagPicker.tsx`) actually composes "catalog item name + description" on inspection — their existing local `matterLabel` is `${uf} — ${description ?? id.slice(0,8)}` (no catalog item at all), and `DeadlineTagPicker.tsx` has no matter-labeling code whatsoever (it's tag-attachment only). The real precedent for a catalog-item-aware composed label is `reports.service.ts`'s `resolveMatterLabel`/`matterFallbackLabel` (client + catalog item, for the Prazos page's matter column) — different composition than what `casos-lista`'s column needs (catalog item + description, no client, since CLIENTE is already its own column). Built a new shared helper, `apps/web/src/modules/matters/components/matterCatalogLabel.ts` — `matterCatalogLabel(matter, catalogItem)`: `"{catalogItem.name} - {short description}"` when both are set, falling back to the same `uf`/description shape as the other precedent when there's no catalog item yet (a `rascunho`). One helper, two call sites (`MattersTable.tsx`'s second column, `MatterDetailView.tsx`'s page title), per the ticket's "not two copies" instruction.
  - Judgment call: descriptions longer than 60 chars are truncated with `…` in the composed label (table cells / a page title shouldn't render an arbitrarily long free-text blob).

  **The two migrations.** `matters.numero_cnj` and `payments.description`, each its own plain Drizzle-generated migration (`packages/db/generate --name=matters-numero-cnj-column` / `--name=payments-description-column`) — two files, not combined, matching the ticket's "two migrations" framing. Plus the hand-written custom migration Trap 2 called out: `20260911231545_matters-numero-cnj-update-grant.sql` adds `grant update (numero_cnj) on "public"."matters" to authenticated` — Postgres column-level grants are additive, so this only *adds* the new column rather than restating/revoking `matters_update_own_tenant`'s existing list. Verified against a real Postgres session (`\dp`-equivalent query on `information_schema.column_privileges`) that `authenticated` actually got `UPDATE` on `numero_cnj` after `supabase migration up`, and covered it with an integration-test regression guard (`matters.service.test.ts`'s new "numeroCnj is nullable..." case explicitly round-trips a null→value→null edit, which would silently no-op if the grant were missing). `payments.description` needed no grant change (blanket grant on that table already), confirmed via a plain create+list round trip in `payments.service.test.ts`.

  **The bucketing-helper extraction.** Moved the vencido/hoje/próximos grouping out of `reports.service.ts`'s `getPrazosCriticos` into `deadlines.service.ts`'s new `getPrazoBuckets(matterId?)`, re-exported via `deadlines.controller.ts` (same precedent `dueDateHighlight` set). It calls the module's own `listDeadlines({ status: "pendente", matterId })` internally — no `matterId` from `reports.service.ts` (tenant-wide), a real one from the new `MatterPrazosCard`. `reports.service.ts`'s `getPrazosCriticos` now only resolves each bucketed row's `matterLabel` (client + catalog item) — the one piece of cross-module knowledge that has no business living in `deadlines.service.ts`.
  - Test-coverage note: this move genuinely changes *how* `getPrazosCriticos` is tested (it no longer calls `listDeadlines`/`dueDateHighlight` directly — it delegates to `getPrazoBuckets`, which does), so `reports/test/reports.prazos.test.ts`'s mock target moved from `deadlines.controller`'s `listDeadlines`/`dueDateHighlight` to its new `getPrazoBuckets` — same behavioral assertions (matterLabel resolution, counts, grouping), same two test cases, still green. The vencido/hoje/próximos delegation/grouping test itself (mocking `deadlines.repository.ts` this time, since `getPrazoBuckets` does its own I/O) moved to a new `deadlines/test/deadlines.prazoBuckets.test.ts`, plus the one new case the spec asked for (`matterId` forwarded to `listDeadlines` when scoping to a single matter).

  **Prazos card specifics.** New `apps/web/src/modules/deadlines/components/MatterPrazosCard.tsx` (lives in the `deadlines` module, same cross-module-component-into-`matters`-detail pattern `TagPicker`/`PaymentPanel` already establish). Badge slot reproduces `TagPicker`/`DeadlineTagPicker`'s chip markup (dot + name, tag's own border color) as a small read-only `TagChip`, rather than reusing the interactive picker itself — this card only ever *displays* a deadline's first tag, never attaches/detaches one. "+ Novo prazo" opens the existing `DeadlineDialog` (extended with a new optional `initialMatterId` prop, pre-filling the matter `<select>` — still changeable, not locked) rather than a second create form. All status-pill/badge copy (Atrasado/Pendente/● Fatal) is title-case text rendered uppercase via CSS (`uppercase` class), same idiom already used across this ticket's other pills, not literal all-caps strings.

  **Judgment call — `MattersTable.tsx` drops the standalone "Excluir" (soft-delete) button.** The wireframe's AÇÕES column is a bare chevron only, and the ticket explicitly says edit/archive actions "live inside casos-detalhe" — but casos-detalhe's own checklist (back + Editar caso row, then the four cards) never adds a delete/archive trigger either. Read this as the wireframe intentionally not drawing a delete affordance in this pass (a matter's lifecycle already has an `arquivado` status settable via the edit dialog) rather than a place I forgot to add one. `softDeleteMatter` stays fully implemented and tested at the controller/service level, just not wired to any button after this ticket — flagging in case that reading is wrong.
